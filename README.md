# FindMyPhoto — система хранения и обработки фотографий с соревнований

**FindMyPhoto** — веб-сервис для централизованной загрузки, хранения, обработки и поиска фотографий со спортивных соревнований.

Проект разработан в рамках выпускной квалификационной работы бакалавра в МГТУ им. Н. Э. Баумана.

Система ориентирована на мероприятия, в которых участники идентифицируются по стартовым номерам: мотоспорт, беговые соревнования, велогонки, триатлон и другие дисциплины.

Платформа позволяет фотографам загружать большие наборы изображений, организаторам — управлять соревнованиями и доступом к материалам, а участникам — находить и скачивать свои фотографии.

## Основные возможности

- регистрация и авторизация пользователей;
- ролевая модель пользователей;
- управление соревнованиями и их этапами;
- массовая загрузка фотографий;
- хранение оригинальных и производных изображений;
- асинхронная обработка фотографий;
- автоматическое создание превью;
- создание версий изображений с водяным знаком;
- поиск фотографий по этапу соревнования;
- поиск фотографий по стартовому номеру;
- интеграция с внешним сервисом распознавания стартовых номеров;
- добавление фотографий в пользовательскую коллекцию;
- скачивание отдельных изображений и наборов фотографий;
- разграничение доступа к оригиналам изображений;
- административное управление пользователями и соревнованиями.

## Роли пользователей

В системе предусмотрены четыре основные роли:

- **Участник** — поиск, просмотр и скачивание доступных фотографий;
- **Фотограф** — возможности участника + загрузка фотографий;
- **Организатор** — управление своими соревнованиями и правами доступа;
- **Администратор** — управление пользователями, ролями, статусами и всеми соревнованиями.

Права пользователя определяются не только его ролью, но и принадлежностью конкретных объектов: например, организатор может управлять своими соревнованиями, а пользователь может получить отдельное разрешение на скачивание оригиналов.

### Компоненты

- **Frontend** — пользовательский интерфейс на React и TypeScript;
- **Backend** — REST API и бизнес-логика на Go/Gin;
- **PostgreSQL** — пользователи, соревнования, этапы, фотографии, права доступа и другие метаданные;
- **MinIO** — объектное хранилище оригинальных и обработанных изображений;
- **Redis** — очередь фоновых задач обработки;
- **Worker** — получение и обработка асинхронных заданий;
- **Image Processing Service** — отдельный C++/CUDA-сервис обработки изображений;
- **OCR Service** — внешний сервис распознавания стартовых номеров.

## Обработка фотографий

Обработка изображений вынесена из основного HTTP-запроса и выполняется асинхронно.

Общая последовательность:

1. Пользователь выбирает фотографии в web-интерфейсе.
2. Frontend разбивает большой набор на части размером до **200 файлов**.
3. Backend проверяет права пользователя.
4. Оригинальные изображения сохраняются в **MinIO**.
5. Метаданные фотографий сохраняются в **PostgreSQL**.
6. Backend помещает задачи обработки в очередь **Redis**.
7. Клиент получает `202 Accepted` и идентификатор загрузки.
8. Фоновый worker получает задачи из Redis.
9. Изображения пакетно передаются в сервис обработки.
10. Формируются превью и версии с водяным знаком.
11. Результаты сохраняются обратно в MinIO.
12. Backend обновляет метаданные и статус обработки.
13. Frontend периодически получает текущий прогресс загрузки.

Такой подход позволяет не удерживать HTTP-запрос открытым во время обработки большого количества изображений и не блокировать основной backend ресурсоёмкими операциями.

## GPU-обработка изображений

Для ресурсоёмкой обработки изображений разработан отдельный сервис на **C++/CUDA**.

Сервис используется для пакетной обработки фотографий и позволяет перенести параллелизуемые операции на GPU.

В частности, сервис используется при формировании производных изображений:

- уменьшении разрешения;
- подготовке изображений для web-просмотра;
- создании версий с водяным знаком.

При отсутствии подходящего GPU архитектура позволяет использовать CPU-обработку.

В рамках ВКР было проведено сравнение CPU- и CUDA-обработки. При небольших пакетах разница невелика, однако при обработке большого количества фотографий преимущество GPU становится значительно заметнее.

## Хранение данных

Файлы изображений и структурированные данные хранятся раздельно.

### PostgreSQL

В реляционной базе данных хранятся:

- пользователи;
- соревнования;
- этапы соревнований;
- фотографии;
- версии изображений;
- стартовые номера;
- права доступа;
- refresh-токены.

### MinIO

В объектном хранилище размещаются:

- оригинальные фотографии;
- превью;
- изображения с водяным знаком;
- обложки соревнований.

Такое разделение позволяет не хранить большие бинарные объекты непосредственно в PostgreSQL.

## Поиск по стартовым номерам

Фотография может быть связана с одним или несколькими стартовыми номерами участников.

Для автоматического определения номеров предусмотрена интеграция с отдельным сервисом распознавания.

После получения результатов распознавания найденные номера сохраняются в базе данных и могут использоваться для фильтрации фотографий внутри соревнования.

OCR-сервис является внешним компонентом и не входит в состав данного проекта.

## Развёртывание

Компоненты системы контейнеризированы и могут быть запущены с помощью Docker Compose.

```bash
docker compose pull
docker compose up -d
```

Проверить состояние контейнеров:

```bash
docker ps
```

Конкретные параметры подключения к PostgreSQL, MinIO, Redis и другим сервисам задаются через конфигурацию окружения.

> Для публичного репозитория рекомендуется использовать `.env.example`.
> Реальные пароли, JWT secrets и другие секреты не должны храниться в Git.
